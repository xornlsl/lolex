# 게임 ID로 경기 결과 등록

매칭 신청은 기존 흐름을 유지합니다. 매칭 결과 화면은 게임 ID 입력을 기본으로 제공하고, 리플레이 업로드는 보조로 제공합니다. 캡처 업로드 화면은 제거했습니다. 기존 캡처 경기 기록은 유지됩니다.

## 사용 흐름

1. 한국 서버 사용자 설정 경기의 게임 ID를 세트 순서대로 2개 또는 3개 입력합니다. 숫자와 `KR_숫자` 형식 모두 지원합니다.
2. 경기 기록 불러오기를 누릅니다. 닉네임과 등록된 부계정으로 회원을 연결하고, 매칭에서 확정한 포지션을 채웁니다. 닉네임·해시태그는 대소문자를 구분하지 않습니다.
3. 세트별 회원과 포지션을 검수합니다. 자동으로 연결되지 않은 회원과 교체 선수의 포지션은 직접 선택합니다. API의 챔피언·팀·KDA·승패는 편집하지 않습니다.
4. 최종 확정 시 서버가 Riot 기록을 다시 조회합니다. 서버에서 BO3·진영 교대·회원 중복·포지션·기존 등록 여부를 검사한 후 한 트랜잭션으로 저장합니다.

## 기존 기록 유지

- `finish_riot_series`가 기존 `finish_replay_series`를 호출합니다. 경기 기록은 같은 `replay_games` / `replay_participants` 테이블에 저장됩니다.
- `lolex-match-history`와 `get_most_champions`는 변경하지 않습니다. 모스트는 세트별 챔피언·KDA·승패를 집계하고, 레이팅은 기존 규칙대로 시리즈에 한 번 반영합니다.
- 교체 선수와 2세트 이상 출전한 선수의 레이팅 기준도 기존 검증을 사용합니다.
- API 게임 ID에 고유 제약을 적용합니다. 동일 ID를 다른 매칭에 다시 등록하면 경기 상태·통계·레이팅 전체가 롤백됩니다. 이미 확정된 매칭은 재확정할 수 없습니다.
- 기존 리플레이의 중복 확인은 파일 해시 기준입니다. API로 등록한 경기와 게임 ID가 없는 과거 리플레이 기록 사이의 중복은 자동 판별하지 않습니다.

## 배포 순서

1. 기존 스키마가 있는 Supabase에 `supabase/migrations/202610060003_riot_match_results.sql`을 적용합니다.
2. Supabase Edge Functions의 서버 Secrets에 `RIOT_API_KEY`를 등록하고 `RIOT_MATCH_REGION=asia`로 설정합니다. 키는 `VITE_` 변수나 프런트엔드 코드에 넣지 않습니다. 이 기능은 게임 ID로 조회하므로 `RIOT_ACCOUNT_REGION`은 사용하지 않습니다.
3. `lolex-replay-result` 함수를 공유 모듈과 함께 배포합니다.
4. 프런트엔드를 빌드·배포합니다.

배포 권한 및 DB 기본 스키마가 현재 로컬에 없으므로 이 변경은 로컬 구현 상태입니다. 서버 Secret 등록이나 운영 DB 변경은 수행하지 않았습니다.

## 검증

- `npm test`: 입력 형식·권한·10명 검증·닉네임 연결·진영 교대·통계 변조 방지·재조회·중복 충돌·리플레이 보조 경로 검사.
- `npm run build`, `npm run lint`.
- DB 연결 후 `supabase/tests/riot_series_e2e.sql` 실행: 기록과 모스트, 시리즈 레이팅, 참가자·팀·라인 유지, 고유 ID 충돌 시 전체 롤백 확인. 이 테스트는 끝에서 롤백합니다.
- 실제 10명 BO3에서 화면 조회·검수·확정·매칭 기록·모스트·레이팅을 확인합니다. 이전에 조회 성공한 2인 테스트 경기는 10인 저장 검증 대상으로 사용할 수 없습니다.

Riot API 키가 만료되면 오류 안내 후 리플레이 업로드를 이용할 수 있습니다. 개발 키는 24시간마다 만료됩니다. [Riot 키 안내](https://developer.riotgames.com/docs/portal#web-apis_api-keys), [Match API](https://developer.riotgames.com/apis/#match-v5).
